Reflection

Data Quality impact: One specific data quality issue we encountered was missing transaction timestamps. This was especially important because our analysis compares daily sales before hurricane landfall with sales during the seven-day surge period. If a transaction has no reliable date, it could be excluded from the daily analysis or incorrectly assigned to a different day, which could then probably affect the calculated sales increases. To address this, we attempted to recover missing dates using the surrounding transaction records, but only when the records before and after the missing timestamp showed the same calendar day. We also tested this by temporarily hiding timestamps that were originally available to see whether the approach could recover the correct dates. If we had ignored this problem, our daily sales totals could have been incomplete. On the other hand, automatically filling every missing timestamp could have created inaccurate information. Overall, this showed us that cleaning data is not just about removing missing values, but also about deciding when information can reasonably be recovered and when it is better to leave it unresolved.

ETL trade-offs: One important decision that we made was how we chose to handle negative transaction quantities. There were 130 negative transactions, which could have represented a wide variety of meanings (returns, data entry errors, etc.). We decided to take the absolute value of all these transactions, treating them as data entry errors, and got a total number of sales of 49,825. This number is significant because if we had chosen to ignore the transactions with a negative sign, this would have decreased the total amount of sales. Overall, we chose to keep the negative quantities rather than remove them, which would have skewed up Walmart's predictions of incoming inventory.

Pipeline trust: We created checks throughout each implementation section to increase our confidence/trust in the pipeline, such as row-counting the joins, checking duplicate and missing values, creating SKU mapping assertions, and comparing cleaned tables against the original source tables. We also kept a decision log so that cleaning actions and assumptions were made visible and were not hidden. Implementing these checks in the code makes it easier to detect failures, reproduce results, and retrace our steps. Throughout this project, we saw how inconsistent store IDs, duplicate transactions, missing timestamps, and different product or category labels could affect the results before any actual analysis took place. Overall, this project demonstrated that a reliable pipeline requires consistent validation and documentation, not simply code that runs without producing an error.

Business vs data: A rising or falling trend in sales before landfall may help identify categories or stores to investigate, but it does not directly tell Walmart how much inventory to stock for each product or make decisions for the business. To make a holistic business decision, we also need information about current on-hand inventory, units already on order, distribution-center capacity, shipping times, and local conditions. Data alone will not make decisions, but we can strategize knowing data as context. Similarly, SKU consolidation makes product demand easier to interpret, but it does not prove that every product variant is interchangeable for the business. We would use the analysis to prioritize inventory products, then validate against operational constraints. With more time, we would investigate the mismatched records more closely, verify how the database calculates daily sales, and compare actual sales with inventory changes before making a more confident recommendation.
